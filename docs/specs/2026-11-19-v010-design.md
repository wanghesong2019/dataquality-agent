# DataAgent v0.1.0 设计文档

> 状态：**已定稿，待进入实施计划** ｜ 日期：2026-11-19 ｜ 作者：用户 + Claude Code
> 说明：本文是产品形态与 v0.1.0 边界的设计决策，随仓库开源（对外发布前会译成英文并入 README/docs）。

---

## 1. 意图与为什么（Intent & Why）

把 dataquality-agent 从「求职 demo」升级为**开箱即用的生产级数据质量组件**，长期目标是长成像 Flink/Spark 那样「内核稳定 + 连接器生态自己生长」的基础设施。

**为什么现在、为什么这条路**：

- 「Agentic 数据质量」（多 Agent 巡检→归因→整改→审批闭环）是**空白地带**：传统数据质量工具只检测不归因不整改，而直接对标的 agentic 项目（Aegis DQ ⭐6、CHRONOS/Findata/dqt/OpenBlame）全是 ⭐0~100 的小仓库，**没有开源领导者**。差异化真实存在。
- 用户已明确：**项目开发落地优先级 > 面试应付**。简历是产品做好的自然结果，不是目标本身。

---

## 2. 目标 / 非目标 / 反目标

### 目标（Goals）

1. **内核可嵌入**：检测/归因/整改/报告是一套可 `import` 的干净库，别人能嵌进自己的 pipeline（dbt/Dagster/Airflow/CI）。
2. **引擎可插拔**：通过 `WarehouseAdapter` 接口接入任意数仓/引擎，DuckDB 为参考实现，连接器生态可被社区扩展。
3. **评估可复现**：检测/归因/整改的量化指标由 CI 里的 eval harness 产出，数字与 README 永远对得上。
4. **开箱即用**：`pip install` + `dqagent init/run/eval` 三个命令拿到价值；`dqagent serve` 提供 dashboard/调度/HITL。

### 非目标（Non-goals，v0.1 明确不做）

- 不实现真实数仓的血缘**采集**（OpenLineage/OpenMetadata 对接留接口、后置）。
- 不做多租户 / RBAC / 集群高可用（平台壳的生产化后置到 1.0 前）。
- 不做自研向量数据库 / 大模型（复用 Chroma/BGE-M3/DeepSeek 等成熟组件）。

### 反目标（Anti-goals，做成这样就算失败）

- 把内核逻辑裹死在 FastAPI/LangGraph 运行时里，导致「抽不出来、别人 import 不了」。
- 为一个炫酷的分布式引擎连接器（Spark/Flink）压垮单人开发节奏、又不诚实（见约束 2）。
- 只在 README 里宣称"生产级"，却没有 CI 数字、没有版本契约、没有 CHANGELOG。

---

## 3. 约束（Constraints）

1. **单人开发、成本敏感**：模型走 DeepSeek（闲时半价窗口），避免高成本依赖。
2. **不抬高大数据背景**：重心是 Agent 工程（编排/工具调用/评估/HITL），连接器做到「接口正确、可 demo」，不假装 Spark/Flink 源码级精通。
3. **已有代码基底不能推翻重来**：现有 DuckDB 数仓 + LangGraph 多 Agent + FastAPI + dashboard + 186 测试 + eval harness 是资产，方向是「抽取」而非「重写」。
4. **文档与代码同步开源**：设计文档、英文 README、架构图、CHANGELOG 从 v0.1.0 起就随仓库走，不是事后补。

## 4. 竞品与空白（Prior Art，2026-11-19 实测 star）

| 类别 | 代表项目（star） | 与我们的关系 |
|---|---|---|
| 传统数据质量（只检测） | Great Expectations ~12k、Pandera 4.5k、Deequ 3.7k、whylogs 2.8k、Soda 2.5k、Griffin 1.2k、Qualitis 769 | 无 LLM 归因、无整改闭环 |
| 元数据/血缘目录 | OpenMetadata 15.8k、DataHub 13k、Amundsen 4.8k、OpenLineage 2.8k、Marquez 2.3k、Atlas 2.2k | 有血缘有质量检查，无多 Agent 闭环 |
| LLM/Agent 可观测 | Langfuse 37.6k、Opik 23.5k、Phoenix 12.4k、TruLens 3.7k | 只观测 Agent，不碰数据 |
| 语义层/Text2SQL | Vanna 23.8k、WrenAI 18.3k | 相邻，前提是"数据是好的" |
| **Agentic 数据质量（我们）** | Aegis DQ ⭐6、CHRONOS/Findata/dqt/OpenBlame 均 ⭐0~100 | **空白，无领导者** |

结论：我们的差异化 = 上面前四类都没覆盖的交集——「用多 Agent 做数据质量的**归因 + 整改闭环**」。

## 5. 方案与选择（Approaches）

| 方案 | 形态 | 权衡 | 结论 |
|---|---|---|---|
| A 纯库/SDK | `pip install` 嵌入 | 部署最简、分发最广；但 HITL/审批/报告闭环难表达 | 否 |
| B 纯自托管平台 | `docker compose` 起服务 | 最完整呈现闭环；但单人扛 HA/鉴权/多租户过重 | 否 |
| **C 库内核 + 连接器插件 + 薄平台壳（dbt 模型）** | 内核库 + `WarehouseAdapter` + `dqagent serve` | 同时满足易部署/易对接/易贡献，最像 Flink/Spark 的成长路径 | **选 C** |

**选 C 的证据**：dbt 参考适配器是 `dbt-postgres`、社区有 `#adapter-ecosystem` 频道与 verified 认证；Airflow 用 100+ `providers` 连接器包撑起 3.29 亿次/月下载；而 Griffin（Spark+Livy+ES+MySQL）与 qData/OpenMetadata 的平台路线被第三方评测明确评为"部署运维过重，需组织级投入"。

---

## 6. 已定决策（Decisions）

1. **产品形态 = C（dbt 模型）**：内核库 + 可插拔连接器 + 薄平台壳。
2. **版本从 v0.1.0 起，走 SemVer**：0.x 允许 breaking；1.0 = `WarehouseAdapter`/config/CLI/评估口径全部冻结并向后兼容。
3. **连接器路线图**：
   | 版本 | 连接器 | 目的 |
   |---|---|---|
   | v0.1.0 | DuckDB（参考实现） | 自包含、可 CI、零依赖 |
   | v0.2.0 | Postgres（首个真实引擎） | 证明抽象跨「嵌入→服务」成立 |
   | v0.3.0 | StarRocks（首个真实数仓） | 命中 JD 数仓口径，讲真·OLAP |
   | v0.4.0+ | Trino → Spark SQL | 联邦/大数据，社区或后续版本补 |
4. **第一个真实引擎 = Postgres**（而非 Spark/Flink/StarRocks）：最低成本证明抽象成立，且不越界（约束 2）。

## 7. 目标架构（v0.1 方向，实现细节进实施计划）

```
┌ 薄平台壳（dqagent serve，可选）FastAPI + dashboard + 调度 + HITL
├─────────────────────────────────────────────
├ 内核库 dataquality_agent（可 pip install / import）
│   检测(L0/L1/L2) · 归因 · 整改 · 报告 · 评估
│        │ 依赖
│        ▼
│   WarehouseAdapter 接口（声明：连接 / 只读查询 / 元数据 / 方言差异）
│        ├─ DuckDBAdapter（参考实现）
│        └─ (v0.2) PostgresAdapter / (v0.3) StarRocksAdapter …
└ 可观测（Agent 侧 trace + 成本台账；数据侧后置）
```

**关键抽取（评审决议①，中间态）**：DuckDB 耦合远比 `SafeSQL` 广——`warehouse.py`/`detection/`/`metadata.py`/`remediate.py` 都在直接执行 DuckDB 方言 SQL（`::DATE`/`TRY_CAST`/`DESCRIBE`/`SHOW TABLES`），`run_detection` 签名甚至是 `duckdb.DuckDBPyConnection`。v0.1.0 边界：`WarehouseAdapter` 拥有全部「连接/只读查询/元数据/白名单」，内核所有代码只通过 adapter 碰数仓；但内置 L0/L1 检测器是 **DuckDB 参考实现**（其 SQL 属 DuckDB 方言，作为可插拔 `Detector` 单元，Postgres 版各自重写 SQL）。**不做 SQL 方言翻译层**（v0.2 加 Postgres 时再议）。

**框架 vs 参考实现（谁提供什么）**——本项目是「框架 + 参考电池包」，不是「最优算法产品」：

| 层 | 谁提供 | 内容 |
|---|---|---|
| Agent 编排运行时 | **我们（核心价值）** | 多 Agent 归因图、HITL 审批、eval harness、调度 |
| 数仓连接 | 我们 + 社区 | `WarehouseAdapter`（DuckDB/Postgres/StarRocks…） |
| 检测器 | **我们给参考库** + 用户自研 | L0/L1/L2 内置一套，用户可插拔自定义 |
| 整改策略 | 我们给框架 + 用户给领域规则 | 我们给「生成方案→分级→审批」框架，用户给「什么算高危、怎么修」 |

**四个可插拔接缝**：`WarehouseAdapter`（连数仓）· `Detector`（检测）· `RemediationPolicy`（整改）· `CaseStore/RAG`（领域知识）。

**检测层是"标准件"**：学术上 Wang & Strong(1996) *Beyond Accuracy* 的 15 维度（completeness/accuracy/uniqueness/timeliness/consistency…）是 30 年共识；GE/Soda/Deequ/dbt 内置的检查项都映射到同一批维度，不存在"秘密最优算法"。我们的**差异化不是检测算法，而是围绕它们的 Agent 编排（归因 + 整改闭环 + HITL + eval）**。

## 8. v0.1.0 范围（终稿）

**包含**：

- [ ] 内核抽取：detection/diagnose/remediate/report 与 FastAPI/LangGraph 运行时解耦，成为可 `import` 库；detection 按**内部 `Detector` 协议**注册（L0/L1/L2 为首批内置检测器，L2 作带可选 LLM 依赖的检测器）。
- [ ] `WarehouseAdapter` 接口 + `DuckDBAdapter` 参考实现，内核代码只通过 adapter 碰数仓（评审决议①）。
- [ ] CLI 骨架 `dqagent`：`init` / `run` / `eval`，外加**无 LLM 的 detect-only 模式**（只跑 L0/L1，不需要 key）。
- [ ] 开箱即用：内置样本数据（fixture/生成器）+ `dqagent init` 生成本地配置（消除机器特定绝对路径默认值）。
- [ ] checkpointer 持久化：HITL 审批状态用 SQLite 持久化（LangGraph `SqliteSaver`），**验收线 = 重启后仍能 list/approve 历史 run**（持久 run 注册表 + 重启恢复测试）。
- [ ] CI：**无 LLM 的确定性 eval**（检测 F1 用注入器 ground-truth）作硬门禁；README 数字与 CI 一致（实测测试数 186）。
- [ ] 开源基线：英文 README + 架构图 + CHANGELOG + **LICENSE(Apache-2.0)** + git tag `v0.1.0`。

**不包含（后置）**：

- Postgres/StarRocks 连接器（v0.2/v0.3）。
- 数据侧可观测（质量指标时序 + 漂移告警）与血缘标准导出（OpenLineage）。
- **SQL 方言翻译层**（内置检测器 SQL 随方言自动迁移，v0.2 加 Postgres 时再议）。
- **公开 entry_points 插件系统**（v0.1 用内部 registry；公开插件契约 v0.2）。
- **定时调度作为 headline**（`api/scheduler.py` 代码已在，但不列为 v0.1 交付，后置）。
- **diagnose 报告的 schema 变更**（五个动作的 `lineage/slice/blast-radius/pattern` 字段，v0.2 随功能落地；v0.1 仅文档级）。
- **带 LLM 方差的 eval 指标**（归因/整改/端到端/成本）不进 CI 硬门禁，走闲时手动脚本。
- 前端 dashboard 重构（v0.1 原样保留作为 `serve` 壳；`serve` = dashboard + HITL approve）。

## 11. 评审决议（builder check，2026-11-19）

| # | 问题 | 决议 |
|---|---|---|
| ① | WarehouseAdapter 边界 | **中间态**：adapter 拥有连接/只读查询/元数据/白名单；内置检测器是 DuckDB 参考实现（可插拔 `Detector` 单元）；不做 SQL 方言翻译层（v0.2 再议） |
| ② | 开箱即用数据+离线路径 | 内置样本 fixture/生成器 + `init` 生成本地配置 + 无 LLM detect-only 模式 |
| ③ | CI eval 策略 | 无 LLM 确定性 eval（检测 F1）硬门禁；LLM 方差指标走闲时手动脚本 |
| ④ | HITL 验收线 | 重启后仍能 list/approve 历史 run（持久注册表 + 恢复测试） |
| ⑤ | Detector 接口 | v0.1 内部协议（registry）；公开 entry_points 插件 v0.2 |
| ⑥ | LICENSE + 命名 | Apache-2.0；维持 `dataquality-agent`（包）+ `dataquality_agent`（import）+ `dqagent`（CLI）三合一 |
| ⑦ | diagnose 报告（我定） | v0.1 文档级写"五个动作+证据面"，不改 schema |
| ⑧ | serve 范围（我定） | v0.1 = dashboard + HITL approve；定时调度后置 |

- **事实修正**：测试数实测 186（非 98/174）。
- **校准（归因层）**：简单 LLM 脚手架可能反超手工多 Agent 编排——归因层胜负手是"证据检索 + 证据接地"，避免过度工程化编排（见 `docs/design/2026-11-19-attribution-rca-survey.md`）。
