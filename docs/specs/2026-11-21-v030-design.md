# DataAgent v0.3.0 设计文档：Postgres 连接器 + 声明式 L0 断言目录

> 状态：**待审批** ｜ 日期：2026-11-21 ｜ 依据：`docs/specs/design-philosophy.md` + `docs/specs/2026-11-20-v020-design.md` §7/§8/§9
> 范围：两个子系统——① `PostgresAdapter`（第一个真实引擎连接器）② 声明式 L0 断言目录（YAML 声明 → 生成 detector）。

---

## 1. 意图与为什么

v0.2.x 已经把「一切皆断言，判断皆有据」的主链路在 DuckDB 上证明干净（thin 归因 1.000 / 成本归一 3.6× 胜）。但两件事仍是硬编码、不可配置：

1. **连接器只有 DuckDB**。`WarehouseAdapter` 四原语已是最小接口，但只有 DuckDB 一个实现，接不了真实数仓（Postgres 是 JD 数仓口径的第一站）。
2. **断言写死在代码里**。`rules.py` 的 `run_rule_checks` 硬编码 `check_duplicate(adapter, "orders", ["order_id"])` 这种 Olist 表名列名——「声明」（查什么）与「判定+证据」（怎么证）耦合。用户无法声明自己的断言，只能 fork 代码。

本设计把这两件事分开落地。它们**独立**，本设计分别定稿，实施时拆两个 plan。

### 1.1 业务逻辑从哪来：适配器读的是数据，不是语义

「不声明化 Olist 特有业务规则」会自然引出这个问题：adapter 四原语是读数的唯一通道，那框架怎么「知道」数仓的业务逻辑？

**答案：它不该知道，也从不打算从 adapter 里知道。** 四原语只回答「能读什么」（结构、行、计数），不回答「什么是对的」（业务语义）。这是 philosophy 四缝映射里 `WarehouseAdapter` 的定义——**证据接口，暴露 capability 而非 semantics**——加上 P3「证据按需」：adapter 被问才答，绝不预载元数据。

业务逻辑是「断言」三件套里的 **declaration** 那一半，由人显式给出，框架从不从 schema 猜：

| 业务逻辑 | 谁来声明 | 声明形式 | v0.3.0 处置 |
|---|---|---|---|
| 通用结构约束（唯一/非空/空值率/值域/引用完整） | 用户 | `assertions.yaml` | 子系统二：抽成 YAML |
| Olist 特有业务不变式（时间倒挂/未来日期/金额/状态/邮编） | 框架作者 | `run_consistency_checks` 等内置代码 | 保持硬编码「内置检查」 |

两条都满足 Axiom 1「一切皆断言」，差别只在 **declaration 的语法**：通用约束是「表+列+条件+阈值」，YAML 够表达；Olist 不变式是跨表/跨列的**公式**（如「实付 = Σ 单价×数量 + 运费」），表达它得造一套 SQL/表达式 DSL，YAGNI。

所以非目标「不声明化 Olist 特有业务规则」的准确读法是：**adapter 从来不是业务逻辑的来源，声明才是**。这次只把「能通用化的声明」从代码抽到 YAML，adapter 的角色（证据接口）一动不动。

### 1.2 这次在哲学上推进了哪一步

v0.3.0 不是「加两个功能」，是 **Axiom 1（断言三件套）里 declaration 那一半的落地**：

| 哲学条目 | 本次如何落地 |
|---|---|
| Axiom 1 断言统一性 | declaration（查什么）从代码抽成数据（YAML）→ 声明、判定、证据三件套第一次有了独立载体 |
| Axiom 2 证据一等公民 | 声明式生成的 detector 仍复用 `sample_offending` + `Evidence`，异常仍带 query/rows/expected/actual |
| Axiom 3 确定性优先 | 目录只覆盖 L0 确定性规则，规则先于统计、统计先于 LLM 的次序不变 |
| P3 证据按需 | PostgresAdapter 的 `list_tables`/`describe_table` 仍是被问才答，绝不预载元数据 |
| 四缝 `WarehouseAdapter` | 第一个真实引擎实现，证据接口从「参考实现」变「可接真实数仓」 |

换句话说：**「一切皆断言」在 v0.2 是运行时结构（Evidence 贯穿），v0.3 把它推到配置时——用户不 fork 代码就能声明自己的断言。** 这是从「框架替用户写断言」到「用户向框架提交断言」的半步。

## 2. 目标 / 非目标

**目标**
- `PostgresAdapter` 实现 `WarehouseAdapter` 四原语，能对真实 Postgres 数仓跑完整巡检（检测→归因→整改→审批）。
- 声明式 L0 断言目录：用户用 YAML 声明「表 + 列 + 条件 + 阈值」，框架把它编译成带证据的 `Detector`。
- 现有硬编码 L0 规则迁移到「默认断言目录」驱动（Olist 默认声明 + 用户可覆盖/追加）。

**非目标**
- 不把 HITL 状态库（`RunStore` + checkpointer）换 Postgres——用户已定，本次只做仓库连接器。
- 不声明化 L1 统计（freshness/volume/distribution/schema/lineage）——需历史基线快照概念，顺延。
- 不声明化 L2 语义（自然语言规则是另一套东西）。
- 不写 SQL 方言翻译层（v0.2 §10 决议：方言差异留在检测器参考实现层，`LIMIT` 是通用 SQL）。
- 不声明化 Olist 特有业务规则（time_inversion / future_date / amount_mismatch / state_conflict / zip_inconsistency）——它们跨表/跨字段、SQL 复杂，v0.3.0 保持硬编码，作「内置检查」。

## 3. 约束（v0.2 §9 演进契约，本次必须遵守）

| 稳定接口 | 本次如何对待 |
|---|---|
| `WarehouseAdapter` 四原语 | PostgresAdapter 只实现这四原语，不新增方法 |
| `Detector` 协议（`name` + `detect(adapter, ctx) -> list[Anomaly]`） | 声明式目录的**生成目标**——声明 → 生成 detector |
| `Evidence` 模型 | 声明式断言产生的 `Anomaly` 仍带结构化 `Evidence`（复用 `sample_offending`） |
| `assemble_evidence` 证据包契约 | 不动 |

原则（v0.2 §9）：声明式化是**顺着 `Evidence` 结构往上抽一层**，不是推倒重来；v0.2 的 `sample_offending` + `Evidence` 构造直接复用。

## 4. 子系统一：`PostgresAdapter`

**驱动**：`psycopg`（v3，现代 PostgreSQL 驱动，主动维护；不用 legacy 的 psycopg2）。作为可选依赖（`pip install dataquality-agent[postgres]`），DuckDB 仍是零依赖参考实现。

**构造**：`PostgresAdapter(dsn_or_conn)` —— 对齐 `DuckDBAdapter` 的「包一个已存在连接 或 包一个 DSN」模式。连接走 psycopg 的 `Connection`；DSN 用 libpq 连接串。

**四原语映射**：

| 原语 | Postgres 实现 |
|---|---|
| `execute(sql, max_rows)` | cursor.execute；`fetchmany(max_rows)` 封顶（无 max_rows 用 fetchall） |
| `list_tables()` | `SELECT table_name FROM information_schema.tables WHERE table_schema = 'public'` |
| `describe_table(table)` | `SELECT column_name, data_type FROM information_schema.columns WHERE table_name = %s` → `{col: type}`（表不存在返回 `{}`） |
| `row_count(table)` | `SELECT COUNT(*) FROM {table}` |

**类型名**：`describe_table` 直接回引擎报的类型名（Postgres 是 `integer`/`character varying` 等），**不做方言归一**。schema_drift 检测按「同引擎的快照 vs 现状」比对，跨引擎比对是后置的方言层职责。

**安全**：`describe_table` 用参数化 `%s` 防注入；`execute` 只读（内核经 SafeSQL 白名单护栏）。

**测试**：需要一个真实 Postgres。33-server Docker 起 `postgres` 容器 + 载入一个与 `mini_warehouse` 同构的小 fixture 建表；CI 用 `postgres` service。测试覆盖四原语 + 「Postgres 上跑 `run_detection` 产出与 DuckDB 同构的 Anomaly」。

## 5. 子系统二：声明式 L0 断言目录

### 5.1 YAML 声明格式（dbt 风格）

目录文件 `assertions.yaml`：

```yaml
version: 1
assertions:
  - name: orders_unique_order_id
    type: unique
    table: orders
    columns: [order_id]

  - name: orders_customer_not_null
    type: not_null
    table: orders
    column: customer_id

  - name: orders_delivered_date_null_rate
    type: null_rate
    table: orders
    column: order_delivered_customer_date
    max_rate: 0.05
    where: "order_status = 'delivered'"     # status 分层

  - name: order_items_price_non_negative
    type: value_range
    table: order_items
    column: price
    min: 0                                   # min/max 至少一个，可 None

  - name: order_items_ref_products
    type: referential
    child_table: order_items
    child_column: product_id
    parent_table: products
    parent_column: product_id                # 缺省 = child_column
```

**五种类型**（覆盖可通用化的 L0 规则）与字段：

| type | 字段 | 映射到现有函数 |
|---|---|---|
| `unique` | `columns`（1..n） | `check_duplicate` |
| `not_null` | `column` | `check_null_rate(threshold=0)` |
| `null_rate` | `column` + `max_rate` + 可选 `where` | `check_null_rate` |
| `value_range` | `column` + `min`/`max`（≥1 个） | `check_value_range` / `check_negative` |
| `referential` | `child_table` + `child_column` + `parent_table` + `parent_column?` | `check_orphan` |

公共字段：`name`（唯一 id）、`severity`（可选，缺省 medium）。

### 5.2 内部模型 + 编译器

```python
# 声明 → 断言对象（dataclass，字段 = 声明字段）
@dataclass
class Assertion:
    name: str
    type: str
    table: str
    # ... 类型特有字段
    def check(self, adapter) -> list[Anomaly]:
        # 按 type 分发到现有 check_* 函数，复用 sample_offending + Evidence 构造
```

- `load_assertions(path) -> list[Assertion]`：读 YAML、校验 schema（未知 type / 缺字段 / 值域非法 → 报错，fail-fast）。
- `build_assertion_detector(assertions) -> Detector`：包一个 `detect(adapter, ctx)`，逐个 `assertion.check(adapter)` 合并异常。单个断言失败隔离（不拖垮整次巡检），与现有检测器隔离语义一致。

### 5.3 集成与迁移

现状 `run_rule_checks` 硬编码的**通用** L0 规则（duplicate / negative / value_range / null_rate / orphan）迁移到「默认断言目录」——一个内置的 Olist `assertions.yaml`（或代码内等价默认值），驱动 `_L0Rules` 检测器。

- 用户没提供目录 → 用内置默认（= 现状行为，回归不破）。
- 用户提供 `assertions.yaml` → **整体替换**默认目录（内置 Olist 断言不再跑）；要保留默认再追加，就在 YAML 里显式列出。
- `run_consistency_checks`（跨表 amount/state/zip）+ time_inversion / future_date **保持硬编码**（内置检查，与声明式目录并列运行）。

`run_detection` 增加可选参数 `assertions_path`（或 `Settings` 里加 `assertions_path`），缺省走内置默认。

## 6. 验收线

| # | 验收 | 方式 |
|---|---|---|
| P1 | PostgresAdapter 四原语对真实 Postgres 正确 | 集成测试（Docker Postgres + fixture） |
| P2 | Postgres 上 `run_detection` 产出 `Evidence`-带载的 Anomaly，与 DuckDB 同构 | 集成测试 |
| P3 | 声明目录：`load_assertions` 对合法 YAML 生成断言、对非法 YAML fail-fast | 单元测试 |
| P4 | 声明目录：每种 type 生成的检测器产出带 `Evidence` 的 Anomaly | 单元测试（复用 mini_warehouse） |
| P5 | 无声明目录 → 行为与现状一致（回归） | 现有 218 测试全绿 + 新增 |
| P6 | 只读护栏不松动 | 回归测试 |

## 7. 待 builder 决定 / 我的调用

以下是我作为 builder 的调用（用户可纠正）：

- **驱动选 psycopg3**：现代、主动维护；psycopg2 是 legacy。
- **`where` 用原始 SQL 片段**：目录是用户自配的受信配置（同 dbt 的 test where 子句），不做 SQL 解析；参数化留给 `describe_table` 的 `%s`。
- **声明式目录只覆盖「可通用化」的 5 类**；Olist 特有规则（时间倒挂/未来日期/跨表一致性）保持硬编码，避免为复杂 SQL 造一套过度抽象的声明语言（YAGNI）。
- **两个子系统拆两个 plan**：plan A = PostgresAdapter；plan B = 声明式目录。先 A 后 B（A 小且先立测试基建）。
- **Postgres 测试环境**：33-server Docker 起 `postgres` 容器；CI 加 `postgres` service。

## 8. 反目标

- 不引入 psycopg2（legacy）或 SQLAlchemy（重）；就用 psycopg3 直连。
- 不为 L0 造一套图灵完备的「声明 DSL」；YAML 只表达「表 + 列 + 条件 + 阈值」。
- 不把声明式目录做成运行时热加载插件系统（仍走「启动时加载 → 注册 detector」）。
