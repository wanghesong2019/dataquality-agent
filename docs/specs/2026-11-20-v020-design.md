# DataAgent v0.2.0 设计文档：哲学落地（断言 + 证据 + 薄 Agent）

> 状态：**已定稿（待实施计划）** ｜ 日期：2026-11-20 ｜ 依据：`docs/specs/design-philosophy.md`
> 范围：把「一切皆断言，判断皆有据」从纸面落到代码——① adapter 元数据面 ② evidence 数据结构 ③ agent 拓扑。

---

## 1. 意图与为什么

v0.1.0 已经把形态（dbt 模型：库内核 + 连接器 + 薄壳）和检测三层（L0/L1/L2）立住了。但"证据"目前只是**自由文本**（`Anomaly.evidence` 存的是 `"3 组重复键"` 这种字符串），不是一等公民；Agent 是"取证者"（专职 Agent 拿 SQL 工具在数仓里逛），不是"证据消费者"。

本设计把哲学的三条公理落成**三个具体决策**，让"判断皆有据"变成代码里可检查的东西。

## 2. 现状盘点（要改什么）

| 现状 | 问题 | 落点 |
|---|---|---|
| `Anomaly.evidence: str`（自由文本） | 证据不是结构化的，无法被 eval 检查"证据是否支撑结论" | 决策二 |
| L0/L1 检测只 `SELECT COUNT(*)`，**不抓命中行** | 证据只有"有多少"，没有"是哪几行" | 决策一 |
| supervisor + 3 专职（lineage/sql/cases）+ **LLM 分诊**，专职各自调 SQL 工具取证 | Agent 在"逛数仓"，而非"读证据"；LLM 分诊是一次额外的非确定性调用 | 决策三 |
| `WarehouseAdapter` = execute/list_tables/describe_table/row_count | **已经是对的**（最小、只读、按需），保持 | 决策一 |

## 3. 决策一：adapter 元数据面 —— 按需取证据，不预灌

**决策**：`WarehouseAdapter` 保持最小四个原语，**不新增任何 metadata dump**。

- 业务元数据（血缘）、表权限、术语表**不是 adapter 该自动加载的东西**，它们各归各的接缝：
  - 血缘 → `lineage` provider（归因时按需查，已有 `make_lineage_agent(lineage)`）
  - 权限 → SafeSQL 白名单（执行护栏，不是"要展示的元数据"）
  - 业务术语/相似案例 → `CaseStore / RAG`（检索时按需取）
- **取证下沉到确定性检测层**：L0/L1 检测器在"判定 fail"的那一刻，顺手把**命中行样本**抓回来（`SELECT ... WHERE <触发条件> LIMIT 20`），而不是只 `COUNT(*)`。
  - 代价：每条规则从 1 次查询变 2 次（COUNT + 采样）。
  - 收益：证据从"数字"变"行"；样本 `LIMIT 20` 封顶，token-cheap（cs2680 #6）。
  - 兼容：`execute(sql, max_rows)` 已支持行上限，**无需新增 adapter 方法**。

## 4. 决策二：evidence 数据结构 —— 一等公民

**决策**：新增结构化 `Evidence`，并挂到检测/归因/整改三个产出上。

```python
class Evidence(BaseModel):
    query: str                        # 触发判定的 SQL
    rows: list[dict] | None = None    # 命中行样本（截断，默认 LIMIT 20）
    expected: str | None = None       # 期望（阈值 / 基线 / 规则）
    actual: str | None = None         # 实际观测（count / rate / value）
    lineage: list[str] | None = None      # 上游血缘（归因时补）
    blast_radius: list[str] | None = None # 下游影响面（归因时补）
```

挂载关系（v0.2 是 0.x，允许 breaking）：

| 模型 | 现在的证据字段 | v0.2 改为 |
|---|---|---|
| `Anomaly` | `evidence: str` | `evidence: Evidence`（保留 `.summary` 属性回吐原文本，兼容现有 prompt） |
| `Diagnosis` | `evidence_chain: list[str]` | 保留 `evidence_chain` 做**审计轨迹**（调了哪些工具），新增 `evidence: list[Evidence]` 做**支撑根因的证据** |
| `Remediation` | 无证据字段 | 新增 `evidence: Evidence | None`（提案所依据的根因证据） |

**验收线**（可测试）：一条 `fail` 的异常，`evidence.query` 与 `evidence.rows` **非空**；`evidence.rows` 行数 ≤ 20。

## 5. 决策三：agent 拓扑 —— 做薄

**决策**：把 Agent 从"取证者"收薄为"证据消费者"；确定性层抓证据，LLM 只在三个点介入。

**推荐拓扑**（v0.2）：

```
检测（确定性：L0/L1 抓 rows + schema；L2 语义为可选 LLM 判定方式）
   ↓
归因（单一 Agent：读证据包 {rows, lineage, matched_cases} → Diagnosis，证据接地）
   ↓
整改（Executor 提案 + Critic 评审；风险分级；高危 → HITL）
   ↓
报告
```

具体三条：

1. **去掉 LLM 分诊，改为确定性路由**。`supervisor.py` 里 `_default_assignment` 已经是确定性兜底（upstream 类 → lineage，其余 → sql），**把它提成主路径**。省一次非确定性 LLM 调用，且更稳（cs2680 #4：集中验证）。
2. **3 专职 → 1 归因 Agent（证据消费者）**。当前 3 专职串行跑、各拿 SQL 工具逛数仓；它当初省 token 靠的是"窄上下文"，而一旦确定性层**先把证据抓成有界的证据包**，单一 Agent 的上下文天然就窄了——3 路 fan-out + merge 只剩协调税（Tplanning + Tcommunication + Tmerge），没有并行收益（本来就是串行）。归因 Agent 的输入 = 证据包，输出 = 结构化 `Diagnosis`（带证据）。
3. **保持集中验证 + 证据接地**。归因产出由 diagnose 聚合（已存在）；整改由 Critic 评审（已存在）。LLM 只在三处介入：L2 语义判定、归因推理、整改提案 + 风险——每处都是"输入证据包、输出带证据的结构化结论"。

**单 vs 多，用 eval 裁决**（不靠嘴辩，cs2680 #8）：保留现有 3 专职作为可配置的对照臂，由 eval harness 测**成本归一的成功率 + pass^k**，谁赢留谁。设计默认按"单一归因 Agent"落地，若 eval 证明 3 专职更优则回退。

## 6. 工程规范（验收线）

| # | 规范 | 验收方式 |
|---|---|---|
| N1 | 每条 fail 的 `Anomaly` 带非空 `evidence.query + rows` | 单元测试 |
| N2 | 检测-only 模式确定性：同快照 + 同断言 → 同结论 | 已有（CI 确定性 eval） |
| N3 | 证据样本封顶（LIMIT 20），token-cheap | `evidence.rows` 长度断言 |
| N4 | 只读护栏不松动：SafeSQL SELECT-only + 白名单 + 行上限 | 已有，回归测试 |
| N5 | 归因/整改产出**带证据**，且证据可被 eval 检查 | eval harness 扩展"证据支撑"判定 |
| N6 | 成本归一的成功率 + pass^k（非 pass@k）+ holdout 集 | eval harness 指标扩展 |

## 7. 非目标 / 后置

- SQL 方言翻译层（仍后置，v0.2 加 Postgres 时再议）。
- **声明式断言目录（L0/L1 规则从硬编码 Olist 抽成可配置/可插拔的声明）→ v0.3**：v0.2 先在现有硬编码规则上把"证据采集 + 薄 Agent"这条主链路跑通，不引入声明式化。
- 数据侧可观测（质量指标时序 + 漂移告警）仍后置。
- 公开 entry_points 插件系统（仍用内部 registry）。
- 不推翻现有 LangGraph 骨架，只做"取证前移 + 拓扑收薄"的**抽取式改造**，不是重写。

## 8. 范围与路线图（已定）

- **v0.2.0 = 哲学落地（证据一等 + 薄 Agent）单独交付**；Postgres 连接器顺延 **v0.3.0**。
- 理由：先证明"证据 + 薄 Agent"这条主链路，不与"连接器跨引擎抽象"两件证明缠在一起；主链路在 DuckDB 上证明干净后，v0.3 加 Postgres 时证据采集用通用 SQL（`LIMIT`）天然兼容，无返工。

## 9. 演进接口约定（哪些稳定、哪些会变）

把"留足余地"落成一份可审计的契约：未来迭代（v0.3 声明式断言目录、Postgres 连接器、L2 语义增长、数据侧可观测、公开 entry_points）动到每一处时，都要对照本表。

### 稳定（v0.3 依赖，不破坏）

| 接口 | 说明 |
|---|---|
| `WarehouseAdapter` 四原语（execute / list_tables / describe_table / row_count） | 连接器只实现这四原语；方言差异留在检测器参考实现层，不进 adapter |
| `Detector` 协议（name + detect(adapter, ctx) -> list[Anomaly]） | 声明式断言目录的生成目标——"声明 → 生成 detector" |
| `Evidence` 模型（query / rows / expected / actual / lineage / blast_radius） | 证据一等公民；`rows` 可选（无行型证据）、`lineage`/`blast_radius` 预留归因填充 |
| 证据包接口（`assemble_evidence` 的输出 = 证据文本行列表，喂归因 prompt） | 归因 Agent 的输入契约，LLM 只读它下结论 |

### 会变（v0.3 重构，本节是"预告"而非"现在做"）

| 位置 | 现在 | v0.3 会变成 |
|---|---|---|
| 检测器内部 | 硬编码"查什么"（声明）与"怎么证"（判定 + 证据采集）耦合在代码里 | 抽出 `Assertion = 声明 + 判定策略 + 证据函数`，声明式目录驱动 detector 生成 |
| 证据源列表 | `assemble_evidence` 写死 3 个来源（血缘/schema/案例） | 证据源做成可扩展列表（L2 语义、契约等可加新来源） |

### 原则

- 只为"未来确定会来"的东西留 seam（上表稳定项），不为"可能来"的东西加空抽象（YAGNI）。
- 声明式化是**顺着 `Evidence` 结构往上抽一层**，不是推倒重来——v0.2 的证据采集模式（`sample_offending` + `Evidence` 构造）v0.3 直接复用。

## 10. 反目标

- 不引入 OpenLineage/OpenMetadata 这类血缘采集平台。血缘走**独立的、可插拔的 `lineage` provider**（现在为 demo 硬编码，未来可接 dbt manifest / OpenLineage / 用户声明），归因按需 `upstream(table)` 查询；**无血缘来源时优雅降级**——归因靠 SQL 证据 + schema + 案例仍可工作，血缘只是可选的增强证据源。
- 不把 Agent 收薄到"连语义检测都砍掉"——L2 语义仍是差异点，只是它也是"带证据的断言"。
- 不写 SQL 方言翻译层来"让证据查询跨引擎"，v0.2 证据查询用通用 SQL（`LIMIT`），方言差异留在检测器参考实现层（沿用 v0.1 决议①）。
